### Container Networking Options

```text
HAProxy Container Networking Architectures
├── Host Network Mode (network_mode: host)
│   └── Direct host stack binding (Zero NAT overhead, native HTTP/3 QUIC)
├── User-Defined Bridge (networks: custom_bridge)
│   └── Embedded Docker DNS + NAT port forwarding (-p 80:80 -p 443:443)
├── Direct Subnet Access (driver: macvlan / ipvlan)
│   └── Dedicated physical LAN IP address (Bypasses host IP/port footprint)
└── Multi-Host Cluster (driver: overlay)
    └── VXLAN encapsulation for cross-node container routing (Docker Swarm)

```

### Networking Mode Decision Matrix

| Networking Mode | Performance & Latency | HTTP/3 (QUIC) Efficiency | Client IP Preservation | Container DNS Resolution | Security Isolation | Primary Best Use Case |
| --- | --- | --- | --- | --- | --- | --- |
| **`host`** | **Optimal** (Bare-metal speed, 0% NAT overhead) | **Optimal** (Direct UDP stack access) | **Native** (Full L4/L7 client IP visibility) | **Host Only** (Requires IP/host-port mapping to containers) | **Minimal** (Shares host network namespace) | High-throughput, edge reverse proxy, bare-metal homelabs, heavy QUIC/HTTP3 workloads. |
| **`custom bridge`** | **Moderate** (iptables NAT & `docker-proxy` overhead) | **Sub-optimal** (UDP NAT tracking overhead) | **Requires Headers** (Relies on `X-Forwarded-For` / Proxy Protocol) | **Native** (Embedded Docker DNS resolves container names) | **High** (Isolated virtual network interface) | Standard Docker Compose setups where HAProxy proxies to other containers on the same host by name. |
| **`macvlan` / `ipvlan**` | **High** (Direct kernel sub-interface routing) | **High** (Direct UDP interface access) | **Native** (Appears as a physical LAN device) | **LAN / Host DNS** (Requires external DNS or static IP mapping) | **High** (Isolated on separate MAC/IP) | Environments where the host already binds ports `80/443` (e.g., Unraid, Proxmox, OPNsense) and HAProxy needs its own dedicated LAN IP. |
| **`overlay`** | **Lower** (VXLAN encapsulation overhead) | **Moderate** (Depends on Swarm ingress mode) | **Requires Headers** (Requires `ingress` mode or `host` port publish) | **Native** (Swarm multi-host DNS mesh) | **High** (Encapsulated multi-tenant overlay) | Multi-node Docker Swarm / Nomad clusters distributing traffic across distinct physical worker nodes. |

### Detailed Architectural Analysis

#### 1. Host Network Mode (`network_mode: host`)

Host networking removes the network isolation between the container and the host machine. The container binds directly to the host's physical network interfaces (`eth0`, `br0`, etc.).

##### When to Use

* **High-Throughput & Low Latency:** Bypasses Docker's `userland-proxy` and `iptables` DNAT processing, eliminating packet inspection overhead at high connection rates.
* **HTTP/3 & Native QUIC:** HTTP/3 relies on heavy UDP traffic. Docker's NAT bridge handles high-volume UDP connection tracking inefficiently compared to standard TCP; host mode executes UDP I/O directly on the host kernel stack.
* **Preserving L4 Client IP:** Client IP addresses hit HAProxy's listening sockets natively without being rewritten to `172.17.0.1` (Docker bridge gateway IP).
* **Large Dynamic Port Ranges:** If HAProxy needs to listen on hundreds of ports, host mode avoids thousands of `iptables` rules generated by bridge port bindings.

##### When NOT to Use

* **Host Port Conflicts:** If another service on the host (e.g., Nginx, Apache, Pi-hole, `systemd-resolved`) is already listening on ports `80`, `443`, or `53`, HAProxy will fail to start.
* **Container-to-Container Name Routing:** Containers on `network_mode: host` cannot use Docker's internal embedded DNS (`127.0.0.11`) to resolve other container names (e.g., `http://app1:8080`). You must target backend containers via host-mapped ports (`127.0.0.1:8080`) or host static IPs.
* **Non-Linux Runtimes:** Host mode is not natively supported on Docker Desktop for macOS or Windows due to the underlying Linux virtual machine abstraction layer.

---

#### 2. User-Defined Bridge (`networks: <custom_network>`)

Creates an isolated virtual bridge network interface on the host managed by `iptables`. Ports are exposed to the outside world explicitly via port mappings (`-p 80:80 -p 443:443`).

##### When to Use

* **Container-Name Service Discovery:** HAProxy can use backend container names directly in `haproxy.cfg` (e.g., `server app1 app1_container:8080 check`), and Docker's embedded DNS automatically resolves IP changes during container restarts.
* **Multi-Container Stack Isolation:** Allows HAProxy to reside on a `frontend` network accessible to the outside world, while backend database/application containers sit on an unexposed `backend` bridge network.
* **Avoiding Host Port Clashes:** Allows mapping external non-standard ports to standard internal container ports (e.g., host `:8443` -> container `:443`).

##### When NOT to Use

* **Ultra-High Traffic Environments:** The combination of `iptables` stateful connection tracking and `docker-proxy` userland forwarding introduces CPU utilization overhead under saturated workloads.
* **Direct UDP/QUIC Processing:** Large volumes of HTTP/3 traffic over UDP can cause high host CPU usage due to container bridge NAT traversal.

---

#### 3. Macvlan / Ipvlan (`driver: macvlan`)

Assigns a unique MAC address and IP address directly from your physical LAN subnet to the HAProxy container.

##### When to Use

* **Dedicated LAN IP Address:** You want HAProxy to have its own physical IP (e.g., `192.168.1.50`) on your router/subnet, completely independent of the host system's IP (`192.168.1.10`).
* **Host Port Re-use:** Allows running HAProxy on ports `80/443` even if the host OS uses ports `80/443` for its own management interface (e.g., Proxmox VE, Unraid, TrueNAS).
* **Hardware Firewall Rules:** Enables upstream routers, hardware firewalls, or physical load balancers to filter traffic directly to HAProxy's dedicated IP.

##### When NOT to Use

* **Direct Host-to-Container Communication:** By default, Linux kernel security rules block the host OS from communicating directly with its own child `macvlan` containers over the physical interface (requires an explicit `macvlan` bridge sub-interface workaround on the host to fix).
* **Simple Homelab Stacks:** Adds routing complexity regarding gateway settings, subnets, and static IP management compared to simple bridge or host modes.

---

#### 4. Overlay Networks (`driver: overlay`)

Connects multiple Docker daemons together across different physical hosts in a Docker Swarm cluster.

##### When to Use

* **Multi-Node Clusters:** HAProxy is running on Node A, but needs to load balance across backend application instances running on Node B and Node C over an encrypted VXLAN tunnel.

##### When NOT to Use

* **Single-Host Deployments:** Encapsulating traffic in VXLAN packets on a single physical host adds unnecessary performance overhead without any benefit.
