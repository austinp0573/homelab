# llama-cpp env

ROCm llama.cpp OpenAI-compat server on external `llm-backend` network. one GPU-heavy stack at a time.

| name (key) | default value | purpose + notes |
| --- | --- | --- |
| `COMPOSE_PROJECT_NAME` | `llm-llama-cpp` | Compose project name for this stack's containers, networks attachments, and volume labels. Keep it stable so `nerdctl compose` / `docker compose` reattach to the same project instead of spawning a second copy. Renaming mid-life orphans the old project name and you will think the GPU is free when it is not. I treat this as the identity string for scripts that assume one llama project on the host. |
| `CONTAINER_NAME` | `llama-cpp` | Fixed container hostname and DNS name on `llm-backend`. Open WebUI, AnythingLLM, and friends call `http://llama-cpp:8080/v1` using this exact name. Changing it without updating every client base URL is the classic "connection refused" false alarm. Do not let compose auto-generate a name if other stacks hardcode this one. |
| `RESTART_POLICY` | `unless-stopped` | Keeps the server up across host reboots until you explicitly stop it. That is what you want for a always-on inference backend, not for a one-shot job. If you stop it to free the GPU for Whisper or Comfy, it stays down until you start it again — do not confuse that with a crash loop. Manual `stop` is how GPU exclusivity is enforced here. |
| `LLAMA_IMAGE` | `ghcr.io/ggml-org/llama.cpp:server-rocm` | ROCm-flavored llama.cpp server image that actually sees the AMD GPU. The plain CPU `server` tag will "work" and then surprise you with glacial tokens while still occupying the compose project. Pin or at least record the digest when something finally loads a 32B model cleanly. Mixing this with another ROCm workload on the same GPU is how you get HSA/OOM chaos. |
| `LLM_NETWORK` | `llm-backend` | External user-defined network shared by the LLM family. Create it once with `ensure-network.sh` (or equivalent) before `up`; compose will not create an external network for you. Clients on this network use container DNS, not `HOST_BIND`. Putting llama only on bridge and publishing 8080 is the wrong mental model for Open WebUI. |
| `HOST_BIND` | `127.0.0.1` | Host publish address for the OpenAI-compatible HTTP API. Loopback keeps random LAN clients off the model while still letting you curl from the host. Open WebUI should not use this publish path at all — it should hit `llama-cpp` on `LLM_NETWORK`. Binding `0.0.0.0` without a firewall is an unauthenticated LLM on the wire. |
| `HOST_PORT` | `8080` | Host port mapped to container `:8080`. Useful for host-side smoke (`curl 127.0.0.1:8080/v1/models`) and for pi-agent via `host.docker.internal`. Collides with anything else claiming 8080 on the host, including another llama project. Network peers ignore this and use the container port directly. |
| `MODELS_DIR` | `/opt/llm/models` | Host directory of GGUF files, mounted read-only at `/models` in the container. Keep weights outside the compose tree so upgrades do not touch terabytes of blobs. Wrong path = empty `/models` and a confusing "failed to load model" at start. Do not mount this read-write unless you like the container rewriting your weight store. |
| `MODEL_FILE` | `Qwen3-32B-Q4_K_M.gguf` | Filename only under `MODELS_DIR`; compose turns it into the `-m` argument. Must exist before start or the server exits immediately. Swapping models means changing this and recreating the container — leftover VRAM from a previous load is why you stop other GPU stacks first. Context and VRAM needs follow the file you pick, not the env name. |
| `CTX_SIZE` | `8192` | Passed as `-c`; max context tokens for the loaded model. Higher values eat VRAM fast on 32B-class GGUFs and will OOM where a smaller ctx would have been fine. Keep this aligned with client `token_limit` / `contextWindow` settings or you get silent truncation and weird RAG answers. I bump it only after confirming free VRAM with nothing else on the GPU. |
| `N_GPU_LAYERS` | `999` | `-ngl` offload count; `999` means "all layers that fit" in llama.cpp practice. Lower it only when you are deliberately spilling to CPU because VRAM is tight. Setting `0` turns this into a CPU server while still holding the ROCm devices open — usually pointless next to the embed CPU image. Wrong value plus a huge model is the fast path to thrash. |
| `HIP_VISIBLE_DEVICES` | `0` | Which AMD GPU index the process is allowed to see. On a single-GPU box leave it at `0`; on multi-GPU, pin explicitly so llama does not grab the card you reserved for something else. Empty or wrong index looks like "no GPU" even with `/dev/kfd` mounted. Coordinate this with Whisper, ebook2audiobook, and Comfy — only one heavy consumer at a time. |
| `HSA_OVERRIDE_GFX_VERSION` | *(empty)* | Leave empty unless `rocminfo` and a failed start tell you the gfx IP needs forcing. Wrong override is worse than none: kernels miscompile and you get obscure HIP errors. I only set this after confirming the card's real gfx and the ROCm build's supported list. Do not copy a value from a forum thread for a different GPU. |
| devices / caps | `/dev/kfd`, `/dev/dri`, `video`/`render`, `ipc:host`, `seccomp:unconfined`, `--jinja` | ROCm runtime surface: KFD + DRM devices, group access, loose seccomp, host IPC, and jinja chat templates. Strip any of this "for security" and the GPU path dies in boring ways. `--jinja` matters for modern instruct templates; without it some models format garbage. This stack is inherently privileged relative to a normal app container — isolate with bind and network, not by gutting devices. |
