# borg / borgmatic config

primary path is `template/` (copy per host). `compose-borg/` is an older cron-in-image style. append-only clients: create + check only — prune/compact on the NAS with a non-append key (see `template/scripts/truenas-maintenance.sh`). mixing prune into the client user is how you discover append-only the hard way mid-job.

## secrets

| name (key) | default value | purpose + notes |
| --- | --- | --- |
| `secrets/passphrase.txt` | `<secret>` | one-line repo passphrase loaded via `FILE__BORG_PASSPHRASE` into `BORG_PASSPHRASE`. never put the passphrase in `.env` for the template path — that is the whole point of the file mount. it unlocks every archive in the repo; lose it and the backups are ornamental. common mistake is copying the passphrase into chat logs or `.env` "temporarily" and leaving it there. operational gotcha: mode `600`, root-or-backup-user owned, and include this file in the secret backup procedure separate from the repo itself. |
| `secrets/ssh/id_ed25519` | `<secret>` | client SSH private key used to reach the remote Borg repo. should be authorized as append-only on the server for normal client hosts. it interacts with `BORG_REMOTE_USER`, known_hosts, and the remote forced command. common mistake is reusing a full-access key on laptops so a compromised client can prune. operational gotcha: key permissions must be strict or ssh will refuse it; fix with the template permission scripts rather than `chmod 777`. |
| `secrets/ssh/known_hosts` | *(scanned)* | host key pin for the TrueNAS/SSH endpoint. generate with `scripts/scan-known-hosts.sh` and mount it into the container. prefer this over disabling host key checks in `BORG_SSH_COMMAND`. it interacts with `TRUENAS_HOST` / port — rescan after the server key rotates. common mistake is empty known_hosts plus `StrictHostKeyChecking=no`, which trains you to ignore MITM risk on the backup path. operational gotcha: after NAS rebuilds, update known_hosts before the next backup window or jobs fail loudly (good) or silently skip verification (bad). |

## template `.env`

| name (key) | default value | purpose + notes |
| --- | --- | --- |
| `COMPOSE_PROJECT_NAME` | `borgmatic-template` | project/container name base for a copied host stack. make it unique per host copy so two borgmatic clients on one docker host do not collide. it does not change repo paths by itself but confuses ops when duplicated. common mistake is leaving `template` in the name on a prod host and grepping the wrong stack later. operational gotcha: rename before first up when cloning the template; renaming later orphans containers and volume labels. |
| `CLIENT_HOSTNAME` | `template-host` | hostname inside the container. shows up in logs and can affect how you identify jobs. set it to the real machine role name when you copy the template. it is separate from `BACKUP_NAME` / archive format even when they start equal. common mistake is leaving `template-host` everywhere and then being unable to tell which client's logs you are reading. operational gotcha: keep it stable; churning hostname makes log archaeology annoying without buying security. |
| `BACKUP_NAME` | `template-host` | human naming hint for this backup identity. archive naming still comes from `ARCHIVE_NAME_FORMAT` / yaml. use it as documentation in `.env` so future you knows which host this copy belongs to. common mistake is treating it as the literal archive prefix when `ARCHIVE_NAME_FORMAT` actually controls that. operational gotcha: when cloning templates, change this alongside hostname and repo paths in one edit. |
| `TZ` | `America/Chicago` | container timezone for logs and schedule interpretation related to local time. pick the zone you actually operate in so cron-like schedules and log timestamps match your brain. it interacts with `SCHEDULE_SECONDS` only indirectly — sleep intervals are still wall-clock durations. common mistake is leaving Chicago on a host that lives elsewhere and misreading "when did it run." operational gotcha: changing TZ does not rewrite old log timestamps already emitted. |
| `PUID` / `PGID` | `0` / `0` | runtime uid/gid inside the image for reading sources and writing local repos. `0:0` is the blunt "can read host root mounts" setting many backup containers use. it interacts with `HOST_ROOT` / `APP_DATA_PATH` readability and local repo permissions. common mistake is dropping to a non-root PUID without checking the process can still read `/source/host/etc` and similar. operational gotcha: root-in-container still means protect the docker socket and who can run this compose — this is a privileged backup reader in practice. |
| `BORGMATIC_IMAGE` | `ghcr.io/borgmatic-collective/borgmatic:latest` | borgmatic image tag. pin for prod so an unattended pull cannot change prune/check behavior under you. it interacts with config syntax — major image bumps can require yaml tweaks. common mistake is `:latest` on a critical backup host with no pin recorded. operational gotcha: bump intentionally, run a dry check/create on a non-prod repo first if you can. |
| `RESTART_POLICY` | `no` | default one-shot style: container exits when the job finishes. scheduled profile uses a different long-running pattern. it interacts with how you invoke backups — systemd timers vs in-compose sleep loops. common mistake is setting `always` on a one-shot container and creating a tight restart loop of backup jobs. operational gotcha: match policy to the profile you actually enabled; do not copy `.env` between one-shot and scheduled without reading the compose profiles. |
| `BORGMATIC_VERBOSITY` | `1` | passed through as borgmatic `--verbosity`. higher values spam more progress; lower hide detail you want during incidents. it does not change what gets backed up, only what you see in logs. common mistake is leaving debug verbosity on scheduled runs and filling disks with logs. operational gotcha: bump temporarily while diagnosing, then put it back before the next unattended window. |
| `TRUENAS_HOST` | `10.0.0.1` | SSH host for the remote Borg repo. must be reachable from the client network namespace on `BORG_REMOTE_PORT`. it feeds the constructed `BORG_REMOTE_REPOSITORY` URL. common mistake is leaving the sample IP after DHCP renumbered the NAS. operational gotcha: DNS names are fine if stable; if you change host, update known_hosts in the same change. |
| `BORG_REMOTE_USER` | `borg-user` | SSH username on the NAS, typically locked to append-only Borg commands. must match the authorized_keys forced command setup on TrueNAS. it interacts with the client key and remote repo path. common mistake is using a normal login user that can delete archives from the client. operational gotcha: client should fail prune attempts; if prune works from the client, your server ACLs are wrong. |
| `BORG_REMOTE_PORT` | `22` | SSH port for the remote. non-22 is fine if the NAS listens elsewhere — just keep known_hosts scanning on the same port. it is part of the remote repository URL construction. common mistake is updating firewall DNAT but forgetting this env, then watching timeouts. operational gotcha: test with plain ssh using the same key/known_hosts before blaming borgmatic. |
| `BORG_REMOTE_REPO_PATH` | `/mnt/coldpool/borg/lab/sample-host` | absolute path of the repo on TrueNAS. keep it stable; renaming paths breaks Borg's idea of repo identity unless you intentionally relocate with care. it interacts with `BORG_RELOCATED_REPO_ACCESS_IS_OK` if you ever move it. common mistake is "cleaning up" dataset names and invalidating months of backups' access config. operational gotcha: document the path in the host runbook; sample-host must not ship to prod unchanged. |
| `BORG_REMOTE_REPOSITORY_LABEL` | `truenas` | borgmatic repository label for the remote target. used in logs and for selecting repos in commands. keep it short and stable. common mistake is changing labels casually and breaking scripts that select by label. operational gotcha: labels are not secrets, but inconsistent naming across hosts makes fleet ops harder. |
| `BORG_LOCAL_REPO_PATH` | `/backup/repositories/sample-host` | in-container path for the local repository target. must align with how `LOCAL_REPO_ROOT` is mounted into the container. it interacts with `BORG_LOCAL_REPOSITORY` injection. common mistake is pointing local and remote at the same mental "backup" without initializing both. operational gotcha: local repos still need the passphrase and disk space; filling the local disk fails the whole job if both repos are required. |
| `BORG_LOCAL_REPOSITORY_LABEL` | `local` | borgmatic label for the local repo. pairs with the remote label so dual-target configs stay readable. change only with a clear naming plan across hosts. common mistake is two repos both labeled vaguely and pruning the wrong one on a maintenance host. operational gotcha: keep label vocabulary consistent fleet-wide (`local` / `truenas` is fine). |
| `HOST_ROOT` | `/` | host path mounted read-only at `/source/host` for filesystem backups. usually `/` with yaml picking subtrees under `/source/host/...`. it interacts with `one_file_system` and excludes. common mistake is mounting a narrow host path but leaving yaml sources assuming full `/source/host/home` layout. operational gotcha: always `:ro` — a backup container with write access to `/` is a bad day waiting to happen. |
| `APP_DATA_PATH` | `/srv/example-app` | host path mounted read-only at `/source/app` for application data. point it at the real service data dir on that host. it interacts with `source_directories` in yaml — if yaml still lists `/source/app` but you mount nothing useful, you archive emptiness. common mistake is leaving `example-app` on a prod copy. operational gotcha: consistent path across hosts beats clever per-app mounts you will forget at restore time. |
| `LOCAL_REPO_ROOT` | `./local-repositories` | host directory that backs the container local repo storage. relative paths are relative to the compose project dir. it must exist and have space before first init. common mistake is putting this on a tiny rootfs while backing up large `/source` trees. operational gotcha: this is real backup data — include it in offbox copy plans or accept that "local" is only ransomware-adjacent resilience. |
| `BORG_ENCRYPTION` | `repokey-blake2` | encryption mode used at `borg init` time only. changing it later means a new repository, not a toggle. it interacts with the passphrase file — mode and passphrase together define access. common mistake is editing this in `.env` after init and expecting existing repos to follow. operational gotcha: pick once, document once, never casually "upgrade" encryption on a live repo path. |
| `BORG_COMPRESSION` | `auto,zstd,6` | compression setting fed into `config.yml` via env substitution. affects CPU vs size on every create. it does not re-compress old archives when changed. common mistake is jumping to max compression on a feeble client and blowing the backup window. operational gotcha: change, run one job, compare duration and size before rolling fleet-wide. |
| `BORG_PASSPHRASE_FILE` | `/secrets/passphrase.txt` | path inside the container where the passphrase file is mounted. must match the compose mount and `FILE__BORG_PASSPHRASE` wiring. it is not the host path — confusing those two is a common edit error. common mistake is updating the host secrets path but not the container path env. operational gotcha: if the file is missing at runtime, jobs fail at unlock; do not "fix" by pasting passphrase into `.env` on the template path. |
| `ARCHIVE_NAME_FORMAT` | `template-host` | prefix portion of archive names; yaml appends the timestamp pattern. keep it unique per host so listings stay readable. it interacts with prune keep policies that match by prefix on the maintenance host. common mistake is two hosts sharing the same prefix and making prune/selection scary. operational gotcha: rename prefixes only with a plan for old archives still using the previous name. |
| `BORG_SSH_KEY_FILE` | `/secrets/ssh/id_ed25519` | in-container path to the client private key. must match the secrets mount in compose. used by the ssh command borgmatic invokes for the remote. common mistake is mounting the key elsewhere and leaving this env pointing at a missing file. operational gotcha: pair with correct file modes; ssh is unforgiving about key permissions. |
| `BORG_KNOWN_HOSTS_FILE` | `/secrets/ssh/known_hosts` | in-container path to known_hosts. the strong setup passes this into ssh with strict checking. it interacts with `BORG_SSH_COMMAND` — a command that points at `/dev/null` ignores this file. common mistake is populating known_hosts but leaving the weak ssh command default. operational gotcha: prefer strict checking once the file is populated; leave the weak command only as a bootstrap footnote. |
| `BORG_SSH_COMMAND` | ssh with `StrictHostKeyChecking=no` + `/dev/null` known_hosts | default sample command is weaker than the compose known_hosts wiring deserves. it disables useful host key verification even if `BORG_KNOWN_HOSTS_FILE` is mounted. replace with a command that uses the known_hosts file and `StrictHostKeyChecking=yes` after bootstrap. common mistake is shipping the weak command to prod because the template ran once successfully. operational gotcha: treat tightening this as part of first-time host bring-up, not a later hardening wish. |
| `SCHEDULE_SECONDS` | `86400` | sleep interval between runs for the scheduled profile (86400 ≈ daily). it is not cron syntax — it is a dumb sleep loop duration. it interacts with job duration: if a run exceeds the interval you can overlap depending on how the profile is written. common mistake is setting tiny intervals for "testing" and leaving them in place, hammering the NAS. operational gotcha: after schedule changes, check that only one job runs at a time and that maintenance windows still fit. |
| `HEALTHCHECKS_PING_URL` | `https://hc-ping.com/replace-me` | ping URL used only if the healthchecks block is uncommented in yaml. leaving the placeholder while enabling the block will ping a nonsense URL or fail noisy. it does not send anything while the yaml stays commented. common mistake is setting the env and forgetting to uncomment yaml (or the reverse). operational gotcha: use a unique check per host so silence on one machine is not hidden by another. |
| `NTFY_SERVER` | `https://ntfy.example.test` | ntfy base URL for notifications when that yaml block is enabled. must be reachable from the backup container network path. it pairs with topic and token. common mistake is pointing at a public ntfy without auth on a sensitive backup success/fail channel. operational gotcha: uncomment yaml + set all three ntfy env vars together, then force a failure once to confirm alerts fire. |
| `NTFY_TOPIC` | `borgmatic-sample` | ntfy topic name for this client's notifications. keep per-host topics if you want clean signal. it interacts with ACLs on the ntfy server. common mistake is one shared topic for every host and alert fatigue. operational gotcha: rename topics in both ntfy and `.env` together or you alert into the void. |
| `NTFY_ACCESS_TOKEN` | `<secret>` | bearer token for authenticated ntfy publish. required for locked-down ntfy deployments. store it like any other secret; it is not the Borg passphrase. common mistake is committing a real token in the sample env. operational gotcha: rotate on the ntfy side and update `.env` before the next scheduled run. |
| `APPRISE_URL` | `gotify://example.test/token` | Apprise URL example for alternate notification backends when that yaml block is enabled. scheme and secret are backend-specific. it is inert while commented out in yaml. common mistake is enabling Apprise and ntfy double-alerting without intending to. operational gotcha: test with a manual borgmatic run after enabling so you do not wait overnight to learn the URL is wrong. |

### injected / hardcoded in template compose

| name (key) | default value | purpose + notes |
| --- | --- | --- |
| `BORG_REMOTE_REPOSITORY` | built from user@host:port/path | fully composed remote repo location that yaml `${BORG_REMOTE_REPOSITORY}` expands to. built from the remote user/host/port/path env pieces. do not invent a second source of truth for the remote URL. common mistake is editing only yaml with a hard-coded repo and ignoring the env builder. operational gotcha: change the parts, recreate/re-run, and confirm borgmatic lists the repo you think it does. |
| `BORG_LOCAL_REPOSITORY` | from `BORG_LOCAL_REPO_PATH` | injected local repo URL/path for yaml. keeps local and remote configuration parallel. if you remove local from yaml, this can be unused but still present in compose. common mistake is initializing only remote while yaml still lists both. operational gotcha: dual targets mean dual init — missing local init fails the job even when remote is fine. |
| `FILE__BORG_PASSPHRASE` | passphrase file path | image convention that reads the file into `BORG_PASSPHRASE` at runtime. this is why the template avoids plaintext passphrase in `.env`. it must point at the mounted passphrase file. common mistake is also setting `BORG_PASSPHRASE` in `.env` and losing track of which one wins. operational gotcha: if unlock fails, check mount + file contents + this variable before rotating keys in panic. |
| `BORG_RELOCATED_REPO_ACCESS_IS_OK` | `no` | Borg safety latch against accessing a repo that looks relocated. leave `no` unless you knowingly moved the repo and understand the risk. it interacts with path changes on the NAS. common mistake is flipping to `yes` to silence an error without understanding why Borg thinks the repo moved. operational gotcha: a sudden relocate warning is a stop-the-line event — verify you are not writing to the wrong disk. |
| `BORG_UNKNOWN_UNENCRYPTED_REPO_ACCESS_IS_OK` | `no` | safety latch against touching an unexpected unencrypted repo. leave `no` in normal encrypted setups. it exists to prevent accidental ops on the wrong directory. common mistake is enabling this to "just make the job run" against a path that is not your repo. operational gotcha: keep encryption mode and this flag boring; surprise unencrypted repos deserve investigation, not overrides. |
| `S6_KEEP_ENV` | `1` | s6-related env retention for the image entrypoint. leave as the template sets unless you know the image's supervision model. it is not a Borg feature flag. common mistake is deleting unknown env vars during "cleanup" and breaking the image's env plumbing. operational gotcha: do not strip image-required env when copying compose fragments into other stacks. |

## template `config.yml`

| name (key) | default value | purpose + notes |
| --- | --- | --- |
| `source_directories` | `/source/host/home`, `/source/host/etc`, `/source/app` | paths inside the container that get archived. narrow by default on purpose — widen only with excludes thought through. they must exist via the `HOST_ROOT` / `APP_DATA_PATH` mounts. common mistake is adding `/source/host` wholesale and pulling in enormous virtual filesystems. operational gotcha: after mount changes, `exec` and `ls` the sources once before trusting the next overnight job. |
| `repositories` | remote + local via env | dual repository targets expanded from env. init both or delete one from yaml deliberately. append-only remote still needs a working local if listed. common mistake is commenting one repo in yaml but leaving scripts that assume two. operational gotcha: a failure to write either listed repo fails the create — monitor both disks. |
| `exclude_caches` | `true` | skips cache directories Borg/borgmatic know how to detect. saves space and time without listing every cache path. it interacts with app-specific caches that may still need explicit excludes. common mistake is turning it off for "completeness" and ballooning repos with rebuildable junk. operational gotcha: restores still need package reinstalls for caches you skipped — that is intended. |
| `exclude_if_present` | `.nobackup` | if this marker file exists in a directory, that tree is skipped. handy for scratch dirs and huge rebuildable assets. drop the file deliberately; do not rely on folklore about where it is. common mistake is marking a parent directory and accidentally excluding data you needed. operational gotcha: document marker usage on the host so future mounts do not "lose" trees silently. |
| `one_file_system` | `false` | when `true`, Borg will not cross filesystem boundaries from a source root. `false` is safer for mixed mount layouts until you know you want the restriction. it interacts with `HOST_ROOT=/` and bind mounts. common mistake is setting `true` on `/` and silently skipping mounted app data on another filesystem. operational gotcha: only enable when you intentionally want "this disk only" behavior and have verified mounts. |
| `archive_name_format` | `${ARCHIVE_NAME_FORMAT}-{now:…}` | final archive name pattern combining the env prefix and timestamp. keep it parseable for humans and prune tooling. it interacts with maintenance keep policies on TrueNAS. common mistake is putting spaces or host-uniqueness into the wrong field. operational gotcha: changing format does not rename old archives; expect mixed prefixes during transition. |
| `compression` | `${BORG_COMPRESSION}` | yaml-side compression setting from env. changing env without re-rendering/restarting the job context does nothing. same CPU/size tradeoffs as the env note. common mistake is editing only yaml or only `.env` in a split-brain way. operational gotcha: one source of truth — prefer env → yaml substitution as the template designed. |
| `ssh_command` | `${BORG_SSH_COMMAND}` | ssh command Borg uses for the remote. this is where weak host-key settings actually take effect. tighten in `.env` and keep yaml substituted. common mistake is hardcoding a second ssh command in yaml that overrides your hardened env. operational gotcha: after hardening, run one remote list/create and confirm it still authenticates. |
| `encryption_passphrase` | `${BORG_PASSPHRASE}` | passphrase material for the repo, populated from the file-injected env. never commit a literal passphrase into yaml. it must match the passphrase used at init. common mistake is re-initing a path with a new passphrase and leaving old archives unreachable without realizing. operational gotcha: passphrase rotation is a migration story, not an env flip — plan new repo or re-key procedures deliberately. |
| `checks` | repository + archives, `1 month` | consistency check schedule/policy in borgmatic terms. checks catch bitrot and foot-guns; they also cost time/IO. on append-only clients, checks that require rewrite operations can fail — know what your user can do. common mistake is enabling aggressive checks during the only overnight window and colliding with create. operational gotcha: stagger check intensity on the NAS maintenance path when client rights are limited. |
| `keep_*` / prune | commented | retention/prune settings intentionally commented for append-only client users. prune belongs on TrueNAS with a non-append key via `truenas-maintenance.sh`. enabling prune here against append-only auth just fails (best case) or is misconfigured dangerous (worst). common mistake is uncommenting keep policies because tutorials always show them on the client. operational gotcha: document where prune runs for each repo; client yaml should stay create/check focused. |
| healthchecks / ntfy / apprise / sqlite | commented examples | notification and sqlite hooks ship commented with matching `.env` placeholders. uncomment only the blocks you will actually configure. each block needs its env counterparts set the same day. common mistake is uncommenting everything and getting partial alert spam or sqlite paths wrong. operational gotcha: enable one notifier, prove it, then consider a second — silence is worse than duplicate alerts only if you never tested either. |

## compose-borg (alternate)

cron inside the image. passphrase is plain env (worse than the template file approach). prefer `template/` for new hosts unless you already depend on this layout.

| name (key) | default value | purpose + notes |
| --- | --- | --- |
| `HOSTNAME` | `host` | container hostname for the alternate stack. set to the real host role when deploying. it shows up in logs the same way as the template's client hostname. common mistake is leaving `host` and collecting indistinguishable logs from multiple boxes. operational gotcha: this path still needs unique repo paths even if hostnames collide. |
| `TZ` | `America/Chicago` | hardcoded in compose for this alternate stack (not driven from `.env`). change it in compose if you need another zone. it affects cron interpretation relative to local time. common mistake is editing `.env` TZ and wondering why nothing changed. operational gotcha: treat compose as the source of truth here; do not assume template env parity. |
| `BACKUP_CRON` | `0 2 * * *` | cron schedule inside the image for backup runs. classic crontab five-field format. it interacts with `RUN_ON_STARTUP` for first-boot behavior. common mistake is setting aggressive cron during testing and leaving it to hammer the NAS nightly-plus. operational gotcha: after changes, confirm the image's cron actually reloaded — recreate is safer than assuming live edit. |
| `RUN_ON_STARTUP` | `false` | when `true`, runs a backup as the container starts in addition to cron. useful once for smoke tests. leave `false` in steady state so restarts do not kick off surprise full jobs. common mistake is leaving `true` after bring-up and stacking jobs on every deploy. operational gotcha: flip true → run → flip false → recreate before you call the host done. |
| `BORG_PASSPHRASE` | `<secret>` | required plaintext passphrase in `.env` for this alternate model. different and worse secret story than the template file mount. protect `.env` permissions accordingly. common mistake is copying this pattern into the template path or committing `.env`. operational gotcha: if you migrate to template later, move the secret into `passphrase.txt` and stop carrying it in env. |
| mounts | `/home`, `/etc` → `/mnt/source/…` | source bind mounts that must match `config/config.yml` `source_directories`. always mount `:ro`. path drift between compose and yaml is the usual failure mode. common mistake is adding a yaml source without adding the mount (or the reverse). operational gotcha: keep the mapping table in the host notes; restores depend on knowing what was actually included. |

`.env.example` here is empty — keys live in compose.

## server-side maintenance (`truenas-maintenance.sh`)

| name (key) | default value | purpose + notes |
| --- | --- | --- |
| `BORG_BIN` | `/mnt/fastpool/bin/borg-server/borg` | path to the Borg binary on TrueNAS used by the maintenance script. must be a build that can open the repos you created. it interacts with every prune/check the script runs. common mistake is pointing at an older Borg than the clients used to write. operational gotcha: after NAS upgrades, verify this binary still runs before the maintenance window. |
| `KEEP_DAILY` / `WEEKLY` / `MONTHLY` / `YEARLY` | `7` / `4` / `12` / `2` | retention counts for prune on the server side. this is the real retention policy for append-only client repos. tune to disk budget and recovery expectations together. common mistake is copying client tutorial keep values without considering coldpool size. operational gotcha: dry-run prune first; destructive retention mistakes are not fun to explain. |
| `MODE` | `single` or `walk` | `single` targets one repo path; `walk` walks a root of repos. pick based on how you laid out datasets. it interacts with `REPO_PATH` vs `REPO_ROOT`. common mistake is walking a root that includes scratch repos you did not mean to prune. operational gotcha: start in `single` until you trust the layout, then automate walk carefully. |
| `REPO_PATH` / `REPO_ROOT` | *(host paths)* | target repository path or root of repositories on TrueNAS. must be accessed with a key that can prune — not the append-only client key. wrong key fails; wrong path prunes the wrong data. common mistake is running maintenance with the client append-only credentials. operational gotcha: keep maintenance keys offline/limited to the NAS job and log every run. |
